# #hero

A mobile-browser endless runner whose course is a real 50-100 m stretch of street,
reconstructed from satellite imagery, Street View and OpenStreetMap, with a walkability
score card after each run. Spec lives in `spec/`; this README covers Phase 1 (one real
street, generated by an admin, playable end-to-end) and **Phase 2 (cumulative street model +
dense imagery)**: every street is a canonical, versioned model (reference line on the real road,
a traced footpath, entities with evidence, fidelity per stretch) that gets better each time you
add images, and the game corridor follows it.

Stack: Python 3.12 + FastAPI + SQLAlchemy/Alembic on SQLite, zero-build static frontend
(three.js vendored), Anthropic Claude for the vision/review pipeline, Google Static Maps +
Street View Static, Overpass (OSM). Everything runs with `uv run`.

## Setup

```bash
# from /Users/sai/Workspace/her0 (repo root)
cp .env.example .env                        # then fill in the keys and HERO_ADMIN_PASSWORD
uv sync                                     # verify: uv run python -c "import hero; print(hero.__version__)"
uv run python -m hero.tools.vendor_three    # fetches frontend/vendor/three.module.js; prints "downloaded" or "present"
uv run python -m hero.tools.check_keys      # presence + live check of the keys; prints "result: PASS"
uv run alembic upgrade head                 # verify: uv run alembic current prints the head revision
```

`check_keys` makes one tiny real call per provider (fractions of a cent). A Street View
non-OK is reported as a warning, not a failure. Startup of the server fails with a message
naming any empty required variable.

## Admin: generate a street

Open `http://localhost:8711/admin/` and enter the password (`HERO_ADMIN_PASSWORD` from
`.env`; the UI sends it as the `X-Hero-Admin-Password` header on every admin request).

1. **Login** - the status bar shows spend `$0.00 / $50.00` (`HERO_CLAUDE_BUDGET_USD`), run
   counts, Google request/cache counts and the model names.
2. **Create segment** - type an address or place name (prefilled: *100 Feet Road, Indiranagar*, Bengaluru; pasting
   `lat, lon` works too) and how many metres either way to cover (50-100). Press **Find location**, pick the right
   candidate (use "check on map" if unsure), choose the footpath side, then **Create segment**. The segment is
   centred on the address and is 100-200 m long.
3. **Generate** - press **Generate** on the segment row. The run view
   (`/admin/run.html?id=<run_id>`) opens and polls every 1.5 s while the run is
   `queued|running`: steps with timings (fetch imagery -> detect layout -> detect
   obstacles -> assemble -> review 1 -> review 2 -> finalize), the satellite tile and
   Street View frames, per-pass JSON, each review iteration's top-down preview + critique,
   the final scene JSON, and tokens / USD / Google requests.
4. Expected: `succeeded` in roughly 2-4 minutes, under ~$0.20 per run (hard stop
   `HERO_RUN_BUDGET_USD=2.00`), Google requests <= 6.

Cost and budget notes:

- Every LLM call is priced from `src/hero/llm/prices.json` and recorded; the cumulative
  spend is checked **before** each call. `remaining_usd <= 0` -> `402 budget_exhausted`
  on Generate; raise `HERO_CLAUDE_BUDGET_USD` in `.env` to continue.
- Only one run at a time: a second Generate while one is `queued|running` -> `409
  run_in_progress`.
- Imagery is cached under `data/imagery/` and `data/osm/` keyed by request. **Re-generating
  the same segment makes 0 new Google requests** (the run view shows `0 new / N cached`);
  it does spend LLM tokens again.
- Overpass (OSM) is best-effort: on a 406/502/timeout the pipeline continues without OSM
  and the run view shows `osm_available: false` plus the error.

## Phase 2: the cumulative street model

> The commands in this section are new in Phase 2 and are verified by the Phase-2 gate (`spec/roadmap.md`).

**Concepts.** *Observations* = every image ever fetched/uploaded, with its georeference, hash and cost. The *canonical model*
(`street-model/1`, per segment, versions `v0, v1, v2…`) holds a reference line on the real road, a cross-section that varies along
it (the traced footpath), typed entities with stable ids, per-fact evidence/confidence, contradictions and a fidelity level per
5 m (L0 map only, L1 one viewpoint, L2 multi-view with both sides, L3 with a close-up photo). A *run* adds observations, sends only
the not-yet-fused ones to Claude (batched), merges the result into the model, and publishes the next version plus a plain-language
**run report**. Nothing new to fuse = a free no-op. The game plays the model compiled to a scene (`schema_version: 2`).

1. **Create the street from an address** (as above), then **Check placement** on the segment page
   (`/admin/segment.html?slug=<slug>`): the line must sit on the road. The canonical demo street is created with
   `uv run python -m hero.tools.create_demo_street` (100 Feet Road, Indiranagar, 50 m either way, west footpath) and writes the
   placement image to `docs/evidence/placement.png`; `--db data/hero.db` creates it in a specific SQLite file (migrated to head first;
   default: the configured `HERO_DATABASE_URL`), exit code 2 = the line is not verified against OSM road geometry. The Phase-1 street stays as a *legacy* segment ("placement unverified").
2. **Generate** (segment page or run list). The imagery plan comes from the env defaults (below) and can be overridden per run on the
   segment page ("Add more imagery"): spacing, headings (`forward back left right`), close-up crop zoom, an `s` range.
   Costs per run: Street View ≈ $0.007/frame (cached frames are free), one Claude call per ≤ 8 frames, hard stop `HERO_RUN_BUDGET_USD`
   (default `1.00`) and `HERO_CLAUDE_BUDGET_USD`.
3. **Inspect** on the segment page: version history, the fidelity/coverage map (click a stretch for the photos and "what would improve it"),
   entities with evidence, version diffs; the run page shows the run report (images new vs cached, what changed, fidelity before → after, cost).
4. **Add more imagery** and Generate again: the new version keeps every entity id, raises confidence/fidelity where new images arrived, and the
   report explains the diff. `POST /api/admin/segments/{slug}/imagery` fetches images only (no Claude); the next Generate fuses them.
5. **Play**: the corridor bends with the real road and the footpath lane follows the traced footpath; **About this street** (Ready screen
   and results) says what the model knows in plain language. `uv run python -m hero.tools.load_fixture_street` adds a deliberately curved
   fixture street (`fixture-curved-street`) to the gallery for a visual check of the bending corridor.

Upgrading an existing dev DB: `uv run alembic upgrade head` (revision `0002`), then `uv run python -m hero.tools.import_legacy`
(imports each Phase-1 scene as model v0 `legacy`; idempotent; old scenes keep playing unchanged).

Model slug check: `uv run python -m hero.tools.check_structured` tries each structured-output mode (`forced_tool`, `auto_tool`, `json_text`)
on `claude-sonnet-4-5` and `claude-sonnet-5-5`; `HERO_STRUCTURED_MODE=auto` falls back automatically when a slug rejects forced tool choice.

## Player flow

1. `http://<mac-lan-ip>:8711/` - the gallery lists `ready` segments (one card after the
   first generation) with the satellite thumbnail, best score, run count and walkability.
   Empty state is shown when nothing is generated yet.
2. Tap a card -> `/play/?segment=<slug>` loads the scene, tap to start.
3. Controls: **swipe left/right** (or arrow keys) to change lane, **swipe up / ArrowUp** =
   jump, **swipe down / ArrowDown** = slide. Real detected objects (parked car, pole,
   broken footpath, ...) are image billboards cut from the Street View frames; tokens sit
   on intact footpath and crossings.
4. Crash -> results: score, distance, "New best" when applicable, the walkability card
   (footpath coverage %, hazard count, crossing yes/no, score /100), satellite overlay
   with hazard markers, the detected-objects list with confidence. **Run again** restarts;
   the run is POSTed to the API so best score survives a server restart.

## API

All JSON responses use one envelope: success `{"ok": true, "data": ...}`, failure
`{"ok": false, "error": {"code", "message", "detail"}}` with codes `not_found` 404,
`validation_error` 422, `unauthorized` 401, `run_in_progress` 409, `budget_exhausted`
402, `upstream_error` 502, `internal_error` 500. Every response echoes `X-Request-Id`.
Full contract: `spec/api.md`.

Public (no auth):

| Method | Path | Returns |
|---|---|---|
| GET | `/api/health` | `{status, version, db}` |
| GET | `/api/segments` | ready segments, newest first (gallery cards) |
| GET | `/api/segments/{slug}` | card fields + `start`, `end`, `status`; 404 if unknown |
| GET | `/api/segments/{slug}/scene` | the Scene (`spec/data.md`); 404 `"This street has not been generated yet."` if not `ready` |
| POST | `/api/segments/{slug}/runs` | body `{score, distance_m, tokens_collected, loops, crashed_into_type, crashed_into_id, duration_s}` -> `{run_id, score, best_score, is_new_best, walkability, hazards[]}` |

Admin (header `X-Hero-Admin-Password`):

| Method | Path | Returns |
|---|---|---|
| GET | `/api/admin/status` | budget/spend, run stats, Google counts, models; doubles as login check |
| GET | `/api/admin/segments` | all segments (any status) with `latest_run` |
| POST | `/api/admin/segments` | body `{name, city, start, end, footpath_side}` -> 201 segment |
| POST | `/api/admin/segments/{slug}/generate` | 202 `{run_id, status: "queued"}`; 409 / 402 as above |
| GET | `/api/admin/runs?limit=20` | recent runs summary |
| GET | `/api/admin/runs/{run_id}` | full run for the pipeline view |

Phase 2 additions (admin; full contract in `spec/api.md`): `POST /api/admin/segments/{slug}/generate` (optional body
`{imagery: {...}, run_budget_usd}`), `POST …/imagery` (fetch only), `POST …/observations/upload`, `GET …/observations`,
`POST …/placement-preview`, `GET …/model`, `GET …/model/versions/{n}`, `GET …/model/diff?from=&to=`, `GET …/model/coverage`,
`GET …/model/entities[/{id}]`, `GET /api/admin/runs/{id}/report`. `GET /api/segments/{slug}/scene` returns Scene v1 or v2
(`schema_version`); the gallery list gains an additive `model` block.

Static: `/` gallery, `/play/`, `/admin/`, `/admin/run.html`, `/admin/segment.html`, `/js/*`, `/css/*`,
`/vendor/*`, `/media/{imagery|crops|previews|uploads}/...` (served from `HERO_DATA_DIR`).

## Tests

Tests run on the production engine (SQLite) against a separate file from
`HERO_TEST_DATABASE_URL` (default `data/hero_test.db`), migrated and dropped by
`tests/conftest.py`. Integration and e2e tests call the real Anthropic and Google APIs with
the keys in `.env`.

```bash
# from /Users/sai/Workspace/her0 (repo root)
uv run playwright install chromium                          # once, for tests/e2e
uv run pytest tests/unit -q                                 # fast, no network
uv run pytest tests/integration -q                          # recorded fixtures; Google/Nominatim live where marked; no Anthropic beyond 3 tiny probes
uv run pytest tests/e2e -q                                  # Playwright, phone viewport, fixture street (no generation)
uv run pytest tests/live -q -s 2>&1 | tee docs/evidence/phase2-gate.log   # Phase-2 live gate: exactly 2 real generations (+1 free no-op)
# evidence written by tests/live: docs/evidence/{placement.png,phase2-gate.json,phase2-server.log}; REAL spend (about $0.3-0.6 per generation)
```

The Phase-2 live gate performs **two real full generations** on the 100 m demo street (forward+back, then all four
headings) and reports the total Anthropic spend from the app's own cost records (budget ≈ $0.5-1.0 each); everything else
is deterministic (recorded fixtures, `ReplayLLM`). Test databases are per process (`data/hero_test_<pid>.db`), so test
runs can overlap. Boot check on a spare port: `HERO_PORT=8713 uv run hero-serve` then `curl -s http://127.0.0.1:8713/api/health`
(port 8711 is the dev server's).

## Observability

Logs are JSON lines on stdout (structlog). Key events:

- `http.request` - one per request: method, path, status, duration, `request_id`.
- `pipeline.step` - one per pipeline step: `run_id`, `segment_slug`, `step`, `status`, timing.
- `llm.call` - one per Claude call: `run_id`, `step`, `model`, tokens, `cost_usd`, latency.
- Phase 2: `observation.ingested`, `model.merge`, `model.published`, `fusion.noop`, `fusion.report`.

## Model slug and end-of-life

The vision and review models are configurable via `HERO_VISION_MODEL` / `HERO_REVIEW_MODEL` (default
`claude-sonnet-5-5`, set in `src/hero/llm/defaults.py` after the Phase-2 spike). The Anthropic SDK warns that
`claude-sonnet-4-5` reaches end-of-life on **2026-11-30**. `claude-sonnet-5-5` accepts plain calls but rejects the forced
`tool_choice` Phase 1 used (HTTP 400); Phase 2's client supports `auto_tool` and `json_text` structured output
(`HERO_STRUCTURED_MODE=auto` falls back by itself), and `uv run python -m hero.tools.check_structured` records which mode each
slug passes. On 2026-10-30 `claude-sonnet-5-5` passed `auto_tool` and `json_text` (failed `forced_tool`), so it is the default and the
client uses the non-forced modes for it (see `NOTES.md`). `claude-sonnet-4-5` remains selectable until its EOL.
`src/hero/llm/prices.json` carries a `claude-sonnet-5-5` row (rate assumed equal to 4-5; verify).
